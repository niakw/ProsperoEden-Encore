# NS2 research: lawful homebrew validation without a Switch 2

Updated 2026-10-30. Scope: `research/ns2-ps5-compatibility` only. None of these
fixtures is a commercial game, a dump, firmware, title key or complete proof
of Switch 2 emulation on PlayStation 5.

## Reproducible independent graphics test

Workflow: `.github/workflows/ns2-research-homebrew.yml` (two independent jobs: Blockfall Vulkan and HBLauncher native AArch64 ABI).
Commands on Ubuntu with `libvulkan-dev`, `spirv-tools` and Mesa:

```sh
python3 tools/check-ns2-homebrew-corpus.py --self-test
python3 tools/check-ns2-homebrew-corpus.py --output build-ns2-homebrew
g++ -std=c++20 -O2 -Wall -Wextra -Werror \
  tools/ns2/test_homebrew_vulkan_corpus.cpp \
  -o build-ns2-homebrew/vulkan-test -lvulkan
VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.x86_64.json \
  build-ns2-homebrew/vulkan-test \
  build-ns2-homebrew/app.vert.spv \
  build-ns2-homebrew/app.frag.spv \
  build-ns2-homebrew/app.comp.spv
```

Validation thresholds:
1. **Acquisition:** every external input matches its original, fixed Git
   content SHA-1, length, SPIR-V magic, execution model and Vulkan 1.0 validator.
   Any mismatch fails closed. No outside code is executed by the downloader.
2. **GPU module:** actual `vkCreateShaderModule` for vertex, fragment and compute.
3. **Pipelines:** actual `vkCreateGraphicsPipelines` for vertex + fragment
   and `vkCreateComputePipelines` using ABI 1 storage buffer descriptor.
4. **Execution:** `vkCmdDispatch(1,1,1)`, fence wait, and a *readback assertion*
   that the Blockfall compute shader sets its game-initialized flag.
5. **Boundaries:** a software Vulkan/Mesa host test is not a PS5 GPU test;
   the fixture is never advertised as a Nintendo Switch 2 game or
   automatically injected into Encore's production shader cache.

The **HBLauncher CPU ABI** job retrieves only commit
`18b4748ba98eeac7df17beb5d3418985eb74897c`, builds and runs its
upstream host and QEMU AArch64 ABI tests. That verifies the source SDK
runtime and entry trampoline, not Encore's Dynarmic JIT, Nintendo HLE or PS5.
Its package format uses a custom `manifest.json` (`abi: 3`, `kind: native`)
and is not an NSO/NSP game.

Third-party artifacts are fetched into CI ephemeral directories and are not
committed, vendored, mirrored or attached to releases. The test implementation
and its provenance tool are independently authored under Encore's GPL license.

## N3q — independently built HOS NSO0 loader-admission fixture

Test source: [switch2pc](https://github.com/ctj01/switch2pc)
`examples/hello/hello.S` pinned to source revision
`f1d25d5f92f62f46c4dcf92556757bdf72d5b073`
and verified original Git blob
`dff85100e23fe38ccde75d2034dd2a45ff89a54c`.
CI uses a cross-compiler to assemble original AArch64 SVC code; Encore's
independently authored script packages it into a standard `NSO0` header.
The original fixture is Switch-compatible *generic HOS homebrew*, not
Switch 2-only firmware, content or a verified game.

The **actual experimental NS2 ExeFS loader** now invokes
`Eden::NS2::ExeFS::PreflightNso` for all modules only when the
parsed NPDM identifies a Switch 2 process. That bounds on-disk code
segments, stored/compressed byte lengths, guest virtual layout, BSS, and
the final image allocation *before* the maintained NSO loader is called.
It rejects mismatched sizes and huge/overlapping segments without
affecting the current Switch 1 load path; the final release gate
continues to reject all experimental switches.

The host test invokes that same production-linked preflight with malformed
and valid synthetic headers, then an independently cross-built real NSO0.
It is a **header admission** test, not an end-to-end
`AppLoader_NSO::LoadModule`, Dynarmic execution, NPDM emulated process,
Switch 2 software boot, or a test on actual PS5 GPU hardware.

## N3r — guest AArch64 from actual NSO0 on the maintained Dynarmic JIT

An independent source file `switch2pc/examples/hello/hello.S` is pinned by
Git commit and source Git blob, cross-assembled for AArch64, and packaged
in an NSO0. The existing `PreflightNso` checks its real NSO0 segment
layout before the text segment is installed into the official maintained
Dynarmic A64 JIT test environment.

A separate test runs every *actual guest AArch64 instruction* with
`Dynarmic::A64::Jit::Step`, tracks `svcOutputDebugString`, SleepThread,
GetSystemTick, notification-only Break, and ExitProcess, and verifies the
real guest string, register arguments, monotonic tick check and exact
six-call trace. It uses a minimal deterministic host-SVC handler solely
for testing and a strict instruction cap to prevent guest hangs.

CI: `.github/workflows/ns2-research-jit.yml` builds the maintained x86-64
Dynarmic and runs both this NSO test and the existing LSE/RETA/LDAPR tests.
This is **real guest AArch64 execution from an NSO0** but still **not**
execution through Encore's full `AppLoader_NSO::LoadModule` process,
Horizon/NS2 HLE services, CPU6 scheduler or native PS5 JIT. Therefore it
does not validate Nintendo Switch 2 game compatibility.

## N3s — three NSO0 segments plus BSS before Dynarmic JIT

The cross-built public HOS AArch64 NSO0 test now stages its **full virtual image**:
text, rodata, data, zero-filled alignment gaps and BSS. The two synthetic
non-executable segment markers are verified at their original virtual offsets.
Instruction stepping is restricted to the text segment. The six SVC calls
still come from the pinned independently published AArch64 guest program.

This uses a **host-only NSO image stager**, not the production
`AppLoader_NSO::LoadModule`, `KProcess`, HLE services or native PS5 runtime.
It proves NSO0 guest image layout plus Dynarmic execution, not a Switch 2 game boot.

## N3t — native PS5 NSO owner, opt-in entry validation

The actual native PS5 `AppLoader_NSO::LoadModule` is now guarded by
`PreflightNso` at function entry, before its memory-layout prepass or
allocations. This source override is selected **only** under
`EDEN_NS2_METADATA_EXPERIMENTAL=ON` and
`EDEN_NS2_EXEFS_EXPERIMENTAL=ON` with `PS5_NATIVE`. Default Switch 1 and
release paths preserve the unchanged full Encore PS5 NSO loader, including
sparse-BSS and ZBIC behavior. The NS2 admission guard now accepts the native
ZBIC flag (bit 7) only alongside compressed segments.

CI syntax-checks this actual loader source; GCC and Clang exercise header
bounds and ZBIC flags. This is a **production-source entry safety path**,
not yet demonstrated full `KProcess` creation, HLE services or NS2 boot.

## N3u — actual KProcess module-memory readback (opt-in)

After each real `AppLoader_NSO::LoadModule` in the experimental NS2
ExeFS process path, the owner now reads **up to 16 uncompressed, unmodified
NSO text bytes** from `process.GetMemory().ReadBlock` and checks those
bytes against the original NSO file, at the module's virtual code address.
It fails closed if the file read, guest read, header validation or comparison
fails; compressed and patched/dumped code are explicitly skipped to avoid
false mismatches. Every NS2 process load records its PID, guest entry and
module count only after the successful module loop.

The same small verification helper is tested with host fakes for valid,
corrupted, unreadable, compressed, empty and address-overflow cases. Those
host tests **are not** proof that the full KProcess was instantiated or that
Horizon HLE services executed. A signed-off native, authorized ExeFS fixture
and actual full-core execution are still required before claiming NS2 boot.

## N3v — real Encore HLE SVC dispatch trace (opt-in)

The existing `Kernel::Svc::Call` source (generated upstream SVC owner) is
copied **during an opt-in native PS5 CMake configure** and augmented by a
small diagnostics-only call. The original vendor file, the 32/64-bit SVC
switches, the CPU thread scheduler and every production HLE handler remain
**unchanged**. The real experimental `AppLoader_DeconstructedRomDirectory`
registers the active KProcess PID only after it loads its modules; then the
real kernel dispatcher can log the first **32 actual guest SVC calls** for
that PID before forwarding to the original HLE functions. There are no
fabricated HLE results; unrelated processes are ignored. Each new NS2 load
resets the bounded trace, with no tracking outside the opt-in PS5 build.

The generated source is checked for its exact owner anchors, syntax-compiled
in CI, and the bounded process-specific gate runs under Clang and GCC. This
makes live native NS2 SVC dispatch **observable on a future authorized boot**;
it is not itself a proof that the kernel invoked those handlers on a console.

## N3w — reproducible paired ExeFS input for a future native process boot

`tools/ns2/build_public_exefs_fixture.py` takes only the already independently
cross-assembled and Git-blob-verified public HOS AArch64 NSO0, and creates a
disposable extracted ExeFS directory containing `main` and `main.npdm`.
The NPDM is **synthetic, unsigned** and intentionally uses the experimental
extended ACID location, AArch64 instructions, 39-bit guest address space,
application memory pool, main-thread priority/core and a bounded stack.
This is a research fixture, **not** a Nintendo Switch 2 title/firmware.

The JIT workflow now combines those two physical files into an executable
regression against the **actual** experimental
`FileSys::ProgramMetadata::Load` and `PreflightNso`, verifies guest process
attributes, then separately runs the public AArch64 homebrew in the real
maintained host Dynarmic JIT with its existing deterministic six-SVC stub.
These are distinct validation stages, **not** execution of the paired ExeFS
through `Core::System::Load`, `KProcess`, native PS5 or production HLE.
Full process initialization, actual service execution and native GPU output
remain prerequisites for a real Switch 2 compatibility claim.

### N3w kernel-capability correction for real process eligibility

The generated ACI0 now holds three **real** HOS KAC descriptors in a
non-overlapping 0xC0-byte ACI section. They permit core 0, user thread
priorities 16–63, and only the five distinct SVC numbers observed in the
public homebrew's six-call trace: ExitProcess (0x07), SleepThread (0x0B),
GetSystemTick (0x1E), Break (0x26) and OutputDebugString (0x27). Their
encoding is derived from Encore's maintained
`Kernel::KCapabilities::SetCorePriorityCapability` and
`SetSyscallMaskCapability`, not from an unrestricted capability mask.
The host test checks that the **real** NPDM parser returns these exact words.
This corrects a necessary precondition for `KProcess::LoadFromMetadata`,
not a completed or signed system boot.
