> **Conclusion centrale.** Beaucoup de fonctions système NS1/NS2 sont présentes dans la source active. « Présent » n'est pas « équivalent au firmware », « tests hôtes verts » n'est pas « jeu démarré » et « frontend Ampere inclus » n'est pas « première frame invitée prouvée ». Ce document n'est ni un résultat de test ni une autorisation de changer le code.

**Légende :** SOURCE PRÉSENTE = fonction ou implémentation observée dans l'arbre sélectionné ; ÉCART CIBLÉ = limitation observable directement dans la source ; PARTIEL = couverture d'un domaine sans preuve d'exhaustivité ; NON QUALIFIÉ = comportement manquant sur console ou sans preuve console ; À VÉRIFIER = hypothèse/test différentiel à réaliser, **pas affirmation de code manquant** ; HORS PÉRIMÈTRE = outil, SDK homebrew ou fonctionnalité externe qui ne doit pas être reproduite aveuglément.

**Définition de « manque » pour cet inventaire :**
(A) contrat absent ou incohérent prouvé dans un fichier réellement compilé ; (B) résultat requis toujours absent sur console ; (C) test de conformité par version/service non fait. **C n'autorise pas à prétendre A.** Les matrices ci-dessous conservent cette distinction et privilégient les exigences de jeux réels aux fonctions périphériques.

## 2. Étendue de la bibliothèque et classification

Le catalogue inclut des **spécifications** (SwitchBrew), des **clients homebrew** (libnx/libounce), des **réimplémentations** (Atmosphère, Lichii, Eglantine), des **outils de reverse engineering** (NSTool, Ghidra, envytools) et des **standards du pilote hôte** (Khronos/Mesa/AMD). Aucune de ces familles ne remplace à elle seule une observation de Nintendo Horizon en version NS2.

La couverture complète s'entend **par domaine technique de la bibliothèque**, pas par implémentation de chaque API, syscall, codec, instruction GPU ou mode réservé à tous les firmwares. La liste de commandes exhaustive exigerait un diff automatique versionné entre tables SwitchBrew, binaires système et interfaces du code natif; les tables du présent audit énumèrent les anomalies démontrées et les surfaces majeures non qualifiées, **sans inventer des absences**.

Périmètre prioritaire : P0 NS2 (Mario Kart World `0400C3F00006E000`, Donkey Kong Bananza `040074A01BF12000`); P1 NS1 FC27 `0100C49025D3E000`; issue P0 relancement FC27 dans le même processus.

### Méthode de contrôle IPC complète mais non invasive

| Champ | À comparer pour chaque appel réel | Erreur à éviter |
|---|---|---|
| Service | nom exact et instance/session | inférer commande NS2 à partir d'un ancien nom NS1 |
| Version | version firmware/SDK/Title ID | considérer SwIPC historique comme documentation NS2 |
| Identifiant | Command ID/TIPC/CMIF et rôle des flags | associer un ID similaire à la mauvaise interface |
| En-tête | taille, raw words, buffer descriptor et PID | répondre ResultSuccess avec un mauvais buffer |
| Objets | moved/copied handles, KSession, KEvent, TransferMemory | rendre un handle nul ou non enregistré |
| État | ordre création→handshake→worker→session→teardown | répondre une fois sans créer l'objet attendu ensuite |
| Observation | retour IPC, PC ou SVC suivant, progression GPU | se contenter d'une ligne « service initialisé » |

**P0 discriminant :** pour MKW, vérifier le chemin `chat:u` / GSV / VI2 issu des travaux ciblés déjà présents, mais **ne pas rouvrir un audit général** si les logs donnent directement un autre service fautif.

## 6. NS2 — Ampere, GMMU, shaders, cache et Vulkan/RADV

**Séparer trois problèmes :** (i) la **création de commandes invitées** reste le P0 observé; (ii) la **compatibilité GA10F** sera nécessaire dès qu'il y aura des commandes; (iii) les conseils d'optimisation RDNA 2 concernent le GPU AMD **hôte**, pas la sémantique NVIDIA **invitée**. Un mot PTX/CUDA documenté dans un papier A100 n'est pas un opcode de jeu GA10F prouvé.

### Cas Ampere instructionnels à suivre

- Le lowerer maintenu [lower_to_maxwell.h](https://github.com/niakw/Prospero.Eden-Encore-vendor/tree/082cd1b77c7df80dc422eae5ba59d9cd33e48dc4/encore-active/ns2-runtime/ampere/shader_recompiler/frontend/ampere/lower_to_maxwell.h) possède des traitements pour `HMMA 0x23c`, `LDGSTS 0xfae`, `DEPBAR 0x91a` et `MEMBAR 0x992`; une absence apparente de `case 0x237` dans ce fichier ne démontre **pas** que le shader incriminé exécute IMMA.
- L'étude NVIDIA Ampere, drako3d et la documentation NVIDIA Open GPU servent à corréler des champs de vraie instruction; elles **ne fournissent pas** un transpilateur compatible PS5 prêt à copier.
- Le convertisseur SPIR-V doit préserver portée mémoire, mémoire partagée, prédicats, ordre de stores et barrières; éviter tout `nop` silencieux sur un mode non compris.
- Les optimisations post-boot d'Eglantine (paquets de copies/bornes) doivent rester **post-boot** jusqu'à preuve que la porte 4 est atteinte par Encore.

## 7. NS2 — bilan de couverture factuel

**Présence avérée dans l'arbre actif :** dossiers NS2 CPU6/kernel/process, loader/NPDM, NVDRV AS/GPU, GSV/graphics supervisor, GPU session et worker, GameChat, font service, frontend Ampere, paramètres shaders, TextureCache ASTC, Vulkan/RADV, pont vidéo et sous-systèmes audio. Cela ne signifie **ni couverture exhaustive du firmware, ni lancement commercial NS2 réussi**.

**Gaps prioritaires soutenus par les preuves :**
1. Progression NS2 après `guest_run_begin` jusqu'à la première soumission GPU invitée (P0 console).
2. Concordance entre main NSO, NPDM et éventuelles bases/updates pour les jeux testés (P0 preuve de contenu).
3. Chaîne de sessions GSV/VI2/NVDRV, événements et erreurs effectivement reçus par le jeu (P0 contrat HLE).
4. Cas instructionnels Ampere et barrières dont le code est partiel, **seulement si** les shaders réels les réclament.
5. GPU throughput, texture ASTC, vidéos et mémoire longue session **après** premier rendu, non comme diversion du blocage présent.

L'absence de premier submit doit conduire à un correctif d'initialisation, service ou progression guest si la cause est démontrée. Ajouter des shaders spéculatifs à l'aveugle ne résoudrait pas la porte 4.

### Derniers correctifs à ne pas considérer comme « validés sur console »

- Le parcours des bindings et la réduction de certaines recherches de plages GPU, la retraite des buffers de quadrilatères, la notification DMA→TextureCache, la garde contre trous GMMU et la synchronisation des clears ont été introduits sur le vendor avant ce snapshot. La source compilée conserve la synchronisation nécessaire; aucune capture FC27 **postérieure au couple de SHAs de ce document** ne confirme un gain visuel ou temporel.
- Le rollback des protections mémoire différées (ancien vendor PR #194) reste un **garde-fou de correction** : réutiliser la même idée exige une nouvelle preuve de durée de vie, map/unmap et cohérence; un test d'absence de crash sur l'hôte n'est pas une image correcte.
- Une source de saccades peut être une attente de pipeline, de fence, une contention BufferCache, une simulation invitée non prête, ou une image réutilisée. **30 FPS moyens** ne départagent pas ces cas.
- Pour FC27, contrôler aussi les mauvaises glyphes, vidéos d'introduction, HUD et réouverture ; **aucune des corrections de DMA seule** ne permet de classer tout le jeu fonctionnel.

### Ce qu'il n'y a pas lieu d'implémenter simplement parce que la bibliothèque le mentionne

- Une pile CUDA/PTX hôte (la PS5 n'embarque pas de GPU NVIDIA).
- Les SDK homebrew Nintendo Switch comme dépendances de compilation PS5 par défaut.

## 15. Limites, risques et maintenance

### Niveaux de preuve à conserver

1. **Écart de source démontré** : ligne/branche du propriétaire compilé, invariant, cas rejeté et source upstream exacts.
2. **Hypothèse causale plausible** : relation avec symptôme, mais absence de preuve du déclencheur sur les logs.
3. **Couverture inconnue** : API/commande non inspectée exhaustivement; ne pas la déclarer absente.
4. **Correctif intégré** : SHA moteur/vendor du code modifié, tests hôtes, preuve de CMake; jamais égal automatiquement à « jouable ».
5. **Comportement console validé** : scène et configuration réelles, durée, métriques et captures nécessaires, absence de régression.

### Méthode pour mettre à jour cet inventaire

- Vérifier **nouveau HEAD du moteur, gitlink réellement sélectionné et SHA vendor**, sans changer le couple arbitrairement.
- Reprendre les seuls domaines avec **nouvelle preuve** (nouvel appel IPC, nouveau shader, nouvelle trace ou résultat console), ne pas refaire la bibliothèque entière.
- Revoir les références versionnées SwitchBrew S1/S2; utiliser SwIPC historique uniquement pour son périmètre NS1.
- Croiser chaque correctif candidat avec l'upstream, les rollbacks, l'ABI, le GPU réel et les licences.
- Mettre à jour **les registres existants** : symptôme → ID → logs → cause → amont → correctif → CI → résultat console → statut.
- Ne pas lancer de build/CI manuel, modifier C++ ou ouvrir de branche en réponse à ce document seul.

**État de ce livrable :** analyse de sources et de preuves historiques sur `582973574aa0` / `082cd1b77c7d`, sans exécution PS5 nouvelle. **Ce que les sources ne permettent pas d'affirmer** : un inventaire parfait de tous les IPC NS2 par firmware; un correctif absolu des textures FC27; la cause unique des saccades ou de l'écran noir NS2; un gain FPS apporté par l'étude.
