## Verified missing upstream RomFS path — source correction candidate

Compared merged [Lichii #159](https://github.com/zortos293/Lichii/pull/159), [2ae4c3e](https://github.com/zortos293/Lichii/commit/2ae4c3e40291cde1fbf8627c9010a6d517f977d3), and [Portablelle/EdGlantine-PS5 PR #46](https://github.com/Portablelle/EdGlantine-PS5/pull/46) with both PS5 source-selected `RomFSFactory::OpenPatchedRomFSWithProgramIndex` units: vendor `encore-active/eden-core/src/core/file_sys/romfs_factory.cpp` and the NUP-substituted `headless/nup_v1_romfs_factory.cpp`. The existing code returns `nullptr` if `content_provider.GetEntry` has no NCA even when `RomFSFactory::file` was populated from the loaded loose ExeFS/NUP. The selected FSP service `OpenDataStorageWithProgramIndex` (cmd 205) forwards to this method and fails on null. A game that requests **its own program index 0** therefore cannot read an otherwise mounted RomFS from this route.

Adapted method: prefer real NCA content; on missing provider only, return the loader's `file` **only when index==0, record type Program and !updatable**. Other program indices, Data/AOC and genuinely updatable packages retain existing behavior. Both source variants use the identical method, with extracted exact-method host C++ regression and optimized/sanitized negative cases. Vendor and engine both require CI validation and new PS5 build before this is called corrected on console.

**Critical limitation:** the uploaded quiet NS2 traces **do not record a cmd 205 call/result**, so this is a confirmed source-coverage defect and candidate boot correction, **not a demonstrated initiating cause** of these specific loading stalls. Do not dismiss other service waits, missing guest GPU command production, NPDM/resource ownership or GPU worker readiness. A new build should include an exit/first-frame requirement rather than be declared fixed from host CI.

## 19 Nov follow-up: bounded NS2 *guest* progress witness (source only)

The native R457 test shows two separate extracted ExeFS NS2 titles with `guest_run_begin`, two 10s/30s loading warnings and no game command sample or game frame. Detailed logging does not include `NS2 real HLE SVC` receipts in either title's captured stderr. This does **not** prove that no SVC occurred, because the existing SVC ring samples only GetInfo/QueryMemory while Detailed Logging is disabled and requires active process registration. The console trace reports that full gameplay Debug logging is not enabled in release builds even when preference is ON; the sampled logger is a separate path.

Source-only observability change: `headless/ns2_loading_svc_snapshot.h` reads the **existing** `Eden::NS2::SvcTrace` 64-entry ring from the selected vendor header at the two *already existing* loading milestones. It records `active_pid`, `tracked_recent` (GetInfo/QueryMemory only in quiet mode), `sampled_first32`, `detailed` and at most two last completed/pending critical SVCs (the existing fail-only formatter). The graphical owner adds **one include and two calls**, no timer, per-SVC instrumentation, cache or render change; the ring code is untouched. The symbol is read from the same strongly linked `core` static target, not a second implementation. `pid=0` on an NS2 load would identify missing trace publication; `tracked_recent=0` with `detailed=0` cannot exclude other SVC calls. See `tools/check-ns2-loading-svc-snapshot-host.py` and its host CI.

This is a **diagnostic-only candidate** to avoid another blind console test. It does not fix the missing first NS2 frame, and has not yet passed native link or console validation. The earlier RomFS index-0 path still needs the same native build/console qualification. FC27 texture regression remains open; newer Lichii #1443 null-TIC 2D + cache marker is already present in `encore-active/eden-core/src/video_core/shader_environment.cpp`; do not re-port blindly. Lichii #1519 fast-draw reuse is not a demonstrated factor with our normal profile's fast GPU disabled.
